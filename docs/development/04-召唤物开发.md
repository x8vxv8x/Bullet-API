# 召唤物开发

## 入口

当前版本的召唤物主模型不再是 Builder，也不再推荐把行为拆成多段模板接口。

召唤物开发入口：

```java
SummonApi.spawn(world, owner, "modid:my_summon");
```

注册类型：

```java
SummonApi.registerType(new MySummonType());
```

对应公开类型：

- `SummonApi`
- `SummonType`
- `SummonSpec`
- `AbstractSummonEntity`
- `Battlefield`
- `SummonHandle`
- `SummonSnapshot`

## 先理解召唤物的定位

当前版本里，召唤物被定义成“持续运行的战斗实体”。

也就是说：

- 类型负责声明默认规格和创建实例
- 实例自己保存行为状态
- 管理器只负责生命周期、同步、槽位、碰撞和世界索引

这和 Minecraft 原生 `Entity` 的建模方式更接近。

## 三层结构

### SummonType

注册表中的类型单例。

负责：

- 提供 `id`
- 提供默认 `SummonSpec`
- 创建新的召唤物实例

### SummonSpec

纯静态配置。

适合放：

- `life`
- `damage`
- `slotCost`
- `texture`
- `color`
- `size`
- `rendererType`
- `collisionShape`
- `followRange`
- `attackRange`
- `leashRange`
- `moveSpeed`
- `acceleration`
- `idleHeight`
- `idleRadius`
- `retargetIntervalTicks`
- `syncIntervalTicks`
- `bodyCollisionIntervalTicks`

### AbstractSummonEntity

真正的运行时实例。

适合放：

- 当前阶段
- 冷却
- dash / burst / channel 等局部状态
- 特殊目标逻辑
- 本体碰撞后的状态切换

## 推荐开发方式

推荐每个召唤物直接写成一个类型类加一个实体子类。

如果逻辑很简单，也可以像内置调试类型那样在类型里直接返回匿名实体类。

## 最小示例

```java
public class MySummonType extends SummonType {
    public MySummonType() {
        super("example:my_summon", new SummonSpec()
                .life(6000)
                .damage(4.0f)
                .slotCost(1)
                .texture("bulletapi:textures/entity/bullet.png")
                .color(0x66CCFF)
                .size(0.8f));
    }

    @Override
    public AbstractSummonEntity createEntity(int id, World world, EntityLivingBase owner,
                                             Vec3d position, int formationIndex, long spawnTick) {
        return new MySummonEntity(id, this, owner, position, formationIndex, spawnTick);
    }
}
```

```java
public class MySummonEntity extends AbstractSummonEntity {
    public MySummonEntity(int id, SummonType type, EntityLivingBase owner,
                          Vec3d position, int formationIndex, long spawnTick) {
        super(id, type, owner, position, formationIndex, spawnTick);
    }

    @Override
    public void tickServer(World world, EntityLivingBase owner, EntityLivingBase currentTarget) {
        if (currentTarget == null && shouldRetarget()) {
            currentTarget = acquireTarget(world, owner);
            resetRetargetCooldown();
        }

        if (currentTarget == null) {
            followOwnerOrbit(owner);
            return;
        }

        setState(SummonState.CHASING_TARGET);
        moveToward(getTargetCenter(currentTarget), getSpec().getMoveSpeed(), 2.0D, 0.7D);
    }
}
```

生成：

```java
SummonApi.spawn(world, player, "example:my_summon");
```

## 运行时原则

当前版本的运行时原则是：

- 召唤物内部状态应收在实例字段里
- 不再推荐用字符串 mode / runtime 参数驱动核心 AI
- 主人命令只保留 `setTarget(...)` / `clearTarget()` 这种高层控制
- 超距恢复、索敌、攻击节奏由实例自己决定

这意味着：

- 以前那种通过运行时字符串参数驱动核心 AI 的写法不再是主路径
- 如果一个 summon 需要特殊阶段切换，应直接写成员变量

## Handle

当前 `SummonHandle` 负责外部合理控制：

- `setPosition(...)`
- `setVelocity(...)`
- `setMotion(...)`
- `setLife(...)`
- `setTarget(...)`
- `clearTarget()`
- `retarget()`
- `returnToOwner()`
- `setState(...)`
- `remove()`
- `snapshot()`

不再推荐也不再提供旧的运行时参数写接口。

## Battlefield

查询世界中的召唤物：

```java
Battlefield.Summons summons = Battlefield.of(world).summons();

int count = summons.count();
List<Integer> ids = summons.ids();
List<SummonSnapshot> all = summons.all();
SummonSnapshot one = summons.get(id);
SummonHandle handle = summons.handle(id);
List<SummonSnapshot> owned = summons.ownedBy(player.getUniqueID());
```

## 本体碰撞

召唤物本体碰撞仍由运行时统一处理。

外部观察方式仍然是：

- `BulletCollisionEvent`

内部处理方式变成：

- 命中后由运行时回调实体的 `onBodyCollision(...)`

这意味着：

- 公共联动仍然走事件
- 单个 summon 的局部反应应写在实体类里

## 常见问题

### 为什么召唤失败

优先检查：

- 是否在服务端生成
- 是否设置了 `owner`
- 类型是否已注册
- 槽位是否足够

### 为什么代码量会变少

因为当前版本推荐把一个召唤物的主要逻辑收敛到一个实体类里。

正常情况下：

- 新增一个 summon，主要新增 1 个类型类
- 行为复杂时，再加 1 个实体类

不再需要再拆：

- target selector
- move controller
- attack pattern
- formation strategy
- mode / runtime param 协议

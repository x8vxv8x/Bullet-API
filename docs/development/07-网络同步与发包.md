# 网络同步与发包

## 总体原则

BulletAPI 当前采用服务端权威同步模型。

- 服务端负责生成、更新、碰撞、伤害判定
- 客户端负责缓存、插帧、渲染
- 业务开发通常不需要手动发送内部同步包

## 当前内部同步对象

### 点弹幕

- `SPacketDanmaku`

### 激光

- `SPacketLaser`

### 召唤物

- `SPacketSummon`

统一注册入口：

- `PacketHandler`

## 发包职责

### 服务端管理器

服务端对象变化时，由内部管理器发包：

- `DanmakuManager`
  - 点弹幕
  - 激光
- `SummonManager`
  - 召唤物

这意味着：

- 调用 `BulletApi.builder(...).spawn()` 后，不需要自己再发生成包
- 调用 `LaserApi.builder(...).spawn()` 后，不需要自己再发生成包
- 调用 `SummonApi.builder(...).spawn()` 后，不需要自己再发生成包

## 客户端接收落点

客户端缓存：

- `ClientDanmakuCache`
- `ClientLaserCache`
- `ClientSummonCache`

这些缓存负责：

- 接收生成包
- 应用更新包
- 处理移除包
- 为渲染器提供运行时数据

## 当前三条同步链

### 1. 点弹幕同步链

服务端：

- 生成 `Bullet`
- `DanmakuManager.spawnBullet(...)`
- 发送 `SPacketDanmaku.createSpawn(...)`

客户端：

- `SPacketDanmaku.Handler`
- `ClientDanmakuCache`
- `RenderHandler`

### 2. 激光同步链

服务端：

- 生成 `Laser`
- `DanmakuManager.spawnLaser(...)`
- 发送 `SPacketLaser.createSpawn(...)`

客户端：

- `SPacketLaser.Handler`
- `ClientLaserCache`
- `RenderHandler`

### 3. 召唤物同步链

服务端：

- 生成 `SummonBullet`
- `SummonManager.spawnSummon(...)`
- 发送 `SPacketSummon.createSpawn(...)`

客户端：

- `SPacketSummon.Handler`
- `ClientSummonCache`
- `RenderHandler`

## 什么时候需要改网络层

一般新增：

- 新弹幕
- 新激光
- 新召唤物
- 新碰撞箱
- 新渲染器

都不需要直接改内部发包逻辑。

只有在以下情况才需要改网络层：

- 服务端对象新增了客户端必须知道的新字段
- 想同步一种全新的运行时对象类型
- 想改变客户端缓存和插值规则

## 扩展内部同步链的思路

如果未来要给某类对象增加新的同步字段，推荐按这个顺序做：

1. 服务端运行时对象增加字段
2. 对应 `SPacket*` 增加序列化和反序列化
3. 客户端 `Cache` 增加接收与应用逻辑
4. 渲染器或客户端逻辑读取新字段
5. 管理器在合适时机发更新包

## 为什么不建议业务侧直接发内部包

原因有三点：

1. 容易破坏服务端权威
2. 容易让客户端缓存与服务端对象脱节
3. 后续内部结构变化时，业务代码会很难维护

因此，开发者通常应优先：

- 调公开 API
- 改管理器
- 改运行时对象

而不是在业务逻辑里直接手工构造 `SPacket*`

## 激光插帧说明

激光同步链当前的表现策略是：

- 服务端快照权威
- 客户端收到快照后立即更新当前状态
- 渲染阶段再做 `prev -> current -> partialTicks` 插帧

这样可以尽量保证：

- 视觉锚点更贴近服务端判定
- 不额外叠加一层追目标滞后

## 调试建议

如果出现“服务端有效但客户端不显示”，建议按这个顺序排查：

1. 是否真的生成了服务端对象
2. 是否真的发了 `SPacket*`
3. 客户端对应 `Cache` 是否成功创建对象
4. `rendererType` 是否有效
5. `RenderHandler` 是否能拿到该对象

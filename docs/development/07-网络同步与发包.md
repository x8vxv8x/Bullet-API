# 网络同步与发包

## 这篇文档的定位

这不是附属 mod 的日常接入入口，而是帮助你理解当前版本的同步边界。

对附属 mod 作者来说，最重要的结论只有一句：

- 使用公开 API / SPI / Event
- 不要直接依赖内部网络包和客户端缓存

## 总体原则

当前版本采用服务端权威模型：

- 服务端负责生成、更新、碰撞、伤害判定
- 客户端负责缓存、插帧、渲染
- 正常业务开发不需要手动发内部同步包

## 哪些是内部同步对象

### 点弹幕

- `SPacketDanmaku`

### 激光

- `SPacketLaser`

### 召唤物

- `SPacketSummon`

统一注册入口：

- `PacketHandler`

这些都属于内部实现，不是附属 mod 的稳定依赖面。

## 发包职责

服务端对象变化时，内部管理器负责同步：

- `DanmakuManager`
  - 点弹幕
  - 激光
- `SummonManager`
  - 召唤物

当前实现上，manager 主要作为运行时协调入口：

- world 内对象存储由内部 runtime store 负责
- 快照转换由内部 snapshot factory 负责
- 发包与差量同步由内部 sync service 负责

这意味着：

- `BulletApi.builder(...).spawn()` 后不需要自己发生成包
- `LaserApi.builder(...).spawn()` 后不需要自己发生成包
- `SummonApi.spawn(...)` 后不需要自己发生成包

## 客户端接收落点

客户端内部缓存：

- `ClientDanmakuCache`
- `ClientLaserCache`
- `ClientSummonCache`

这些类的职责是：

- 接收同步包
- 应用快照
- 为渲染层提供运行时数据

但它们不是给附属 mod 直接调用的公开入口。

## 当前同步链路

### 点弹幕

服务端：

- 创建运行时对象
- 由 `DanmakuManager` 管理生命周期
- 内部发送 `SPacketDanmaku`
- 更新包按字段差量发送：位置、速度、寿命分别带 flag

客户端：

- 包处理器接收
- 写入 `ClientDanmakuCache`
- 渲染层读取

### 激光

服务端：

- 创建运行时对象
- 由 `DanmakuManager` 管理生命周期
- 内部发送 `SPacketLaser`
- 更新包按字段差量发送：起点、方向、长度分别带 flag

客户端：

- 包处理器接收
- 写入 `ClientLaserCache`
- 渲染层读取

### 召唤物

服务端：

- 创建运行时对象
- 由 `SummonManager` 管理生命周期
- 内部发送 `SPacketSummon`
- 快照包按字段差量发送：位置、速度、寿命分别带 flag

客户端：

- 包处理器接收
- 写入 `ClientSummonCache`
- 渲染层读取

## 对附属 mod 作者的实际建议

### 你应该做的

- 用 `BulletApi` / `LaserApi` / `SummonApi` 创建对象
- 用 `Handle` 控制单个对象
- 用 `Snapshot` 读取只读状态
- 用 `Battlefield` 查询世界中的对象集合
- 用类型类和实体子类定义行为
- 用 `Event` 做全局联动

### 你不应该做的

- 直接构造 `SPacket*`
- 直接操作 `PacketHandler`
- 直接修改 `Client*Cache`
- 直接依赖 `DanmakuManager` / `SummonManager`

## 为什么不要直接碰网络层

原因很简单：

1. 会破坏服务端权威
2. 会让客户端缓存和服务端运行时脱节
3. 内部同步结构后续可以调整，但公开 API/SPI 的稳定性要求更高

## 什么时候才需要考虑改网络层

只有在维护核心实现时，才需要关心这些问题：

- 服务端对象新增了客户端必须知道的新字段
- 新增了一种全新的运行时对象类型
- 想调整客户端缓存或插值策略

这类改动属于本体维护工作，不属于附属 mod 日常接入。

## 激光表现说明

当前激光表现策略是：

- 服务端快照权威
- 客户端收到后立即更新当前状态
- 渲染阶段再做插帧

这样做的目标是让视觉结果尽量贴近服务端判定。

## 当前同步策略补充

为了降低大量对象场景下的流量压力，当前内部同步已经尽量使用差量更新：

- 点弹幕：位置 / 速度 / 寿命按需发
- 激光：起点 / 方向 / 长度按需发
- 召唤物：位置 / 速度 / 寿命按需发

这意味着：

- 外部通过 `Handle` 改少量字段时，不会强制重发完整对象
- 客户端缓存需要能够接受局部更新，这已经由内部缓存层处理
- 附属 mod 仍然不需要也不应该自行拼装这些差量包

## 排查思路

如果出现“服务端有效但客户端不显示”，排查顺序建议是：

1. 服务端对象是否真的创建成功
2. 是否通过公开 API 正确创建而不是绕过系统
3. `rendererType` 是否有效
4. 客户端资源和渲染注册是否正确
5. 只有在维护本体实现时，才继续查内部同步链
